# haut-seat-helper

河南工业大学图书馆座位预约辅助程序（个人使用）。

> **当前阶段：只读查询 + 认证预检 + 预约提交流程 + Web 管理面板（第一阶段）。**
> 真实预约需显式开启 `HAUT_ENABLE_REAL_BOOKING=true` 且无暂停旗标；
> 认证失效时一律立即停止。**启动 Web 服务本身绝不会执行任何预约**：
> 新计划默认「已暂停 + 未启用」，全局暂停默认开启。
> Web 面板的部署与运维见 [`docs/web-deploy.md`](docs/web-deploy.md)。

---

## 合规声明

- 本项目仅用于个人、按正常人工操作频率的辅助，**不绕过验证码、身份认证、访问权限或请求频率限制**，不做高频轮询或并发抢占。
- **是否允许自动化预约，请自行查阅学校图书馆《预约规则》/公告/用户协议后确认。** 在规则不明确或明确禁止时，请保持 `HAUT_ENABLE_REAL_BOOKING=false`，只使用只读查询与 `dry-run`。
- 本阶段 `addbooking`（真实预约提交）由 `book` 命令使用，且仅在 `HAUT_ENABLE_REAL_BOOKING=true` 时才会调用；`addbooking(...)` 作为历史别名仍抛 `NotImplementedError`。
- 认证失效（HTTP 200 + 业务 `code=401`）时**立即停止**，不轮询座位、不提交预约、不重试提交。
- 所有认证信息通过环境变量/本地配置文件管理，**绝不写入代码、日志或 Git 仓库**。

## 官方规则与流程（已确认，来自官方页面）

来源：
- [《座位预约规则说明》](https://lib.haut.edu.cn/info/1262/9215.htm)（发布日期 2026-09-03）
- [《图书馆预约系统(新版)使用说明》](https://lib.haut.edu.cn/info/1162/12405.htm)（发布日期 2025-02-18）

### 时间规则

- 图书馆开放时间：07:30–22:00
- 预约时间：07:00–21:30
- 读者只可预约**当天**座位

### 座位预约流程（网页 / 小程序）

1. 使用学校**统一身份认证**账号密码登录（网页版入口 https://wslib.haut.edu.cn/）。
2. 进入「座位预约」→ 选择区域 → 选座（进入座位选择列表）。
3. 选中座位后点击「确定」提交座位信息 → **提示「预约成功」**。
4. 预约成功后可在「预约记录」查看（小程序路径：座位 → 预约记录）。
5. 入馆后系统自动关联人脸识别闸机签到，无需手动签到；未按时到馆记违约并释放座位。
6. 预约时间开始前可取消预约。

### 关于自动化

> 上述两个官方页面均**未提及**自动化、脚本、机器人、第三方工具、批量操作或频率限制。**是否允许自动化预约，官方没有明确说法**，本程序不自行推断，保持 `HAUT_ENABLE_REAL_BOOKING=false`。

## 安装

要求 Python 3.10+。

```bash
cd haut-seat-helper
python -m venv .venv

# Windows
.venv\Scripts\activate
# Linux/macOS
source .venv/bin/activate

pip install -e ".[dev]"
```

只跑 CLI、或只跑 Web 面板：

```bash
pip install -e .          # 仅 CLI（httpx + pydantic-settings）
pip install -e ".[web]"   # CLI + Web 面板（fastapi / uvicorn / jinja2 / python-multipart）
pip install -e ".[dev]"   # 上面全部 + pytest
```

未安装 `[web]` 时 `python -m haut_seat web` 会直接打印安装命令并以退出码 2 结束，
不会启动一个功能不全的服务。

## 配置

1. 复制模板并编辑（可留空，全部使用默认值）：

   ```bash
   cp .env.example .env      # Windows 用 copy .env.example .env
   ```

2. 复制座位偏好配置（可选）：

   ```bash
   cp config/seats.json.example config/seats.json
   ```

3. 关键项说明（详见 `.env.example` 内注释）：

   | 变量 | 默认 | 说明 |
   |---|---|---|
   | `HAUT_BASE_URL` | `https://wslib.haut.edu.cn` | 服务端基地址 |
   | `HAUT_ENABLE_REAL_BOOKING` | `false` | 真实预约开关，当前必须为 false |
   | `HAUT_PAUSE_FILE` | `data/pause.flag` | 暂停旗标文件，存在即暂停真实预约 |
   | `HAUT_SEATS_CONFIG` | `config/seats.json` | 座位优先级配置 |
   | `HAUT_BOOKING_CONFIG` | `config/booking.json` | 预约任务配置（`book` 命令） |
   | `HAUT_LOG_FILE` | `logs/haut_seat.log` | 日志文件路径 |
   | `HAUT_REGIONID` | `16` | 默认查询区域 ID（参考浏览器正常查询；CLI `--regionid` 可覆盖） |
   | `HAUT_PAGE_SIZE` | `10` | 默认每页座位数（CLI `--page-size` 可覆盖） |
   | `HAUT_HTTP_ACCEPT` 等 | 见 `.env.example` | 非敏感请求头（可选覆盖；凭据头由 `HAUT_COOKIE`/`HAUT_AUTHORIZATION` 单独处理） |
| `HAUT_AUTHORIZATION` | 空 | `Authorization` 请求头完整值（**服务端只校验这个头**，必配） |
| `HAUT_COOKIE` | 空 | `Admin-Token=<同一 JWT>`（与 Authorization 配套，两者都需更新） |
| `HAUT_AUTH_SOURCE` | `auto` | 凭据来源：`auto`（较新的一方胜出）/ `browser`（只用快照）/ `env`（只用 `.env`，与从前逐字节一致） |
| `HAUT_AUTH_DIR` | `data/auth` | 容纳快照与浏览器用户目录 |
| `HAUT_AUTH_SNAPSHOT_FILE` | `data/auth/credentials.json` | 受限快照文件（**不提交版本库**；页面永不读取它的内容） |
| `HAUT_AUTH_PROFILE_DIR` | `data/auth/browser-profile` | 持久化浏览器用户目录（减少重复登录） |
| `HAUT_AUTH_BROWSER_CHANNEL` | `msedge` | 复用系统已装的 Edge；**不下载任何浏览器** |
| `HAUT_AUTH_LOGIN_TIMEOUT_S` | `300` | 等待人工完成登录的上限（含输验证码的时间） |
| `HAUT_AUTH_CHECK_TTL_S` | `0.0` | 只读预检结果的复用窗口（秒）。`0` = 完全关闭，行为与从前一致；`>0` 时**只复用 `valid`**，`invalid`/`indeterminate` 一律重新探测 |
| `HAUT_AUTH_MASTER_KEY_FILE` | `data/auth/master.key` | **每用户学校凭据**的加密主密钥文件（首次使用时自动生成 32 字节）。**必须备份**：丢了它，所有用户都必须重新绑定（详见下文「多用户」一节） |
| `HAUT_AUTH_CRED_KEY` | 空 | 主密钥的另一种来源（十六进制 / base64 / ≥16 字节原文）。**配了它就不读、也不改写上面的文件**。别名 `HAUT_CRED_KEY` 同样接受；两个都设时以 `HAUT_AUTH_CRED_KEY` 为准 |
| `HAUT_HTTP_CLIENT_CACHE_MAX` | `8` | 出站 HTTP 客户端的 LRU 条数上限。客户端**按凭据指纹分桶**（多用户下每个用户各一份）；同时活跃的用户数超过它时会反复重建连接池，人多时调大 |
| `HAUT_WEB_HOST` / `HAUT_WEB_PORT` | `127.0.0.1` / `8080` | Web 面板监听地址与端口（**默认只允许本机**） |
| `HAUT_WEB_DB` | `data/web.db` | 面板数据库（管理员哈希、计划、运行记录） |
| `HAUT_WEB_SESSION_SECURE` | `false` | 走 HTTPS 时置 `true`；**只提供 HTTP 时必须保持 `false`** —— 否则浏览器不会回传会话 Cookie，表现为「登录成功却一直回到登录页」（排查见 `docs/web-deploy.md` 第 12 节） |
| `HAUT_WEB_TRUST_PROXY` | `false` | 可选。默认 `false` 时 uvicorn 自己就会解析 `X-Forwarded-For`（只信任本机来源），限流记的已经是真实 IP；置 `true` 则应用自己取该头**最右一项**（代理追加的那一项）。两种都不取客户端可伪造的最左项 |
| `HAUT_WEB_ALLOW_FIRST_RUN_SETUP` | `true` | 是否允许网页创建第一个管理员 |
| `HAUT_WEB_ENABLE_SCHEDULER` | `true` | 后台调度器总开关 |

> Web 相关的完整清单见 `.env.example` 的「Web 管理面板」一节与
> [`docs/web-deploy.md`](docs/web-deploy.md)。改了 `.env` **必须重启服务**才生效。

> `.env` 与 `config/seats.json` 已被 `.gitignore` 排除，不会入库。

## 测试

```bash
python -m pytest            # 全部测试
python -m pytest -v         # 详细输出
python -m pytest tests/test_web_app.py      # 只跑某一模块
```

**测试全部离线**：网络 IO 与预约提交接口一律用替身注入，
提交替身被调用时会**主动抛错**，所以任何一次意外的真实提交都会立刻让测试失败，
而不是被静默吞掉。测试过程中不会向学校服务器发送任何请求。

## 运行

所有命令都不会在开关未开启时提交真实预约：

```bash
# 查看安全开关与配置状态
python -m haut_seat status

# 只读认证预检：验证**当前来源**的凭据是否仍然有效（不提交预约）
python -m haut_seat check-auth

# 只读查看凭据来源与浏览器可用性（不发任何网络请求）
python -m haut_seat auth-status

# 浏览器辅助的**人工**登录：弹出窗口由你本人登录，程序只把令牌取回来存好
python -m haut_seat auth-login
python -m haut_seat auth-login --no-verify        # 跳过登录后的只读复检
python -m haut_seat auth-login --timeout 600      # 慢慢输验证码

# 离线解析脱敏样例
python -m haut_seat query --from-file samples/layout_query_sample.json
python -m haut_seat dry-run --from-file samples/layout_query_sample.json

# 只读在线查询（需网络可达；官方规则仅可预约当天，请把日期换成当天）
python -m haut_seat query --regionid 16 --start "2026-10-16 08:00" --end "2026-10-16 12:00"

# 预约任务（认证预检 → 等待触发 → 查询选座 → 提交）
python -m haut_seat book

# 初始化 Web 数据库（幂等，不删数据）
python -m haut_seat init-db

# 创建 / 重置 Web 管理员（口令交互式输入，不入库明文）
python -m haut_seat create-admin --username 你的用户名
```

## Web 管理面板（第一阶段）

移动优先的管理面板：登录后可以建预约计划、看运行记录、管安全开关。
**完整部署步骤（systemd / nginx / 备份恢复 / 检查清单）见
[`docs/web-deploy.md`](docs/web-deploy.md)**，这里只给最短路径。

```bash
pip install -e ".[web]"
cp .env.example .env
python -m haut_seat web --init-db                    # 建表（幂等）
python -m haut_seat create-admin --username 你的用户名  # 建管理员（口令不回显）
python -m haut_seat web                              # 打开 http://127.0.0.1:8080/admin
```

页面一览：

| 路径 | 内容 |
|---|---|
| `/admin` | 仪表盘：计划概览、最近运行、认证状态、安全开关 |
| `/admin/plans` | 计划列表；新建 / 编辑 / 暂停 / 恢复 / 停止 / 删除 |
| `/admin/plans/{id}` | 计划详情 + 运行记录；含「提交结果未知」的确认入口 |
| `/admin/runs` | 运行记录列表（可按计划过滤）；`/admin/runs/{id}` 为分阶段事件详情 |
| `/admin/auth` | 认证三态状态、只读预检、**人工**恢复流程引导 |
| `/admin/notifications` | 通知设置与事件开关（**发送未实现**，页面如实标注） |
| `/admin/system` | 全局暂停开关、调度器开关、维护清理、运行统计 |
| `/healthz` | 只读健康检查（不含任何凭据，也不暴露凭据状态） |

计划状态区分八种，其中 **「提交结果未知」不等于「预约失败」**，界面文案与颜色都独立：

`待执行` · `运行中` · `已暂停` · `等待认证` · `预约成功` · `预约失败` · `提交结果未知` · `已停止`

安全默认（都不需要额外配置）：

- 只监听 `127.0.0.1`，对外必须经反向代理 + HTTPS；
- 新计划默认**已暂停 + 未启用**；全局暂停默认**开启**；
- 管理员口令用 scrypt 哈希，会话只存摘要，全部状态变更要 CSRF；
- 登录失败按 用户名+IP 限流；**走 HTTPS 时必须手动设 `HAUT_WEB_SESSION_SECURE=true`，Cookie 才会带 `Secure`**（不设则不带，应用不会根据 `X-Forwarded-Proto` 自动判断）；
- 面板不提供 `/docs`、`/redoc`、`/openapi.json`；
- 页面与 API 响应、日志中**绝不出现** Cookie、Authorization、JWT 或口令。

**明确未实现**（页面上也照实标注，不会假装可用）：

| 项目 | 现状 |
|---|---|
| 邮件真实发送（SMTP） | 未实现。`_deliver()` 固定抛 `NotImplementedError`，只记 `skipped`，设置页保存后明确提示「不会真的发出邮件」 |
| 认证自动登录（账号口令） | 未实现。**不处理密码、不识别验证码、不猜登录接口参数**；登录动作始终由人本人完成 |
| 会话自动续期 | 未实现。令牌无 `exp`、无 refresh token、无刷新端点（[`docs/auth-recon.md`](docs/auth-recon.md)）⇒ 周期性重新登录不可避免 |
| 浏览器辅助的**人工**登录 | **已实现**（`auth-login` / 面板按钮）。打开可见 Edge 由你本人登录，程序只把令牌取回来存成受限快照；依赖是可选的 `.[auth]` extra，**不下载浏览器** |
| 远程浏览器登录（无桌面服务器） | **已实现**（`/admin/auth/browser`）。服务器端跑无头 Chromium，画面与键鼠走 HTTP 转发；需要 `playwright install chromium`（装进项目 `.cache/ms-playwright`），**仍然由人本人登录与识别验证码**，全局单会话 |
| 预约路径自动拉起浏览器 | **不做**，且是刻意的（四条理由见下文「为什么预约路径绝不自动拉起浏览器」） |
| 预约结果查询接口 | 未采集，未实现 |

## 复用合法会话（只读查询）

程序复用你在浏览器里正常登录后的会话。取得凭据有两条路（推荐第一条）：
**① 浏览器辅助的人工登录** = `python -m haut_seat auth-login`；**② 手动复制到 `.env`**。
下面演示的是方式②（回退方案，不装任何额外依赖也能用）。
**两个变量都要配**（服务端只校验 `Authorization`，见上文「认证机制」）：

1. 浏览器 DevTools（F12 → Network）中找到任意一次 `/stage-api/` 请求。
2. 把值写入本地 `.env`（已被 `.gitignore` 排除，不会入库），**不要**粘贴到聊天、代码或日志：
   ```bash
   HAUT_AUTHORIZATION=Bearer <Authorization 头的值>
   HAUT_COOKIE=Admin-Token=<Cookie 里 Admin-Token 那一段>
   ```
3. 运行认证预检（只读，不会提交预约）：
   ```bash
   python -m haut_seat check-auth
   ```
4. 预检通过后再做低频、单次只读查询：
   ```bash
   python -m haut_seat query --regionid 16 --start "..." --end "..."
   ```

程序仅把凭据原样作为请求头发送，不打印、不落日志、不写入样例。
会话失效会被**明确识别**（HTTP 200 + 业务 `code=401`，或重定向/HTTP 401/403），
绝不会被当作空座位列表；网络故障与服务端异常则只会被标记为「无法确认」，
不会被误报为掉登录。

## 认证机制与登录有效期（重要）

### 当前认证方式

| 项目 | 实际情况 |
|---|---|
| 认证载体 | **JWT 令牌**（RuoYi 风格）：`HAUT_AUTHORIZATION=Bearer <jwt>` + `HAUT_COOKIE=Admin-Token=<同一 jwt>` |
| 读取位置 | 本地 `.env`（已被 `.gitignore` 排除）；`haut_seat/config.py` 以 `SecretStr` 承接 |
| 传入方式 | `haut_seat/client/http.py` 原样作为 `Authorization` / `Cookie` 请求头发送 |
| 令牌内含信息 | 仅 `{"login_user_key": "<uuid>"}` —— **没有 `exp`/`iat`/刷新标记** |
| 续期机制 | 响应中**无** `Set-Cookie`、无 refresh token、无任何续期字段 |

### 服务端返回什么信号表示认证失效（实测，2026-10-23 更正）

**两条接口的职责不同，不能混用**。以下全部为受控只读实测（只发 GET，不提交任何预约）：

**① `GET /stage-api/api/seatbook/layout/query`（座位查询）—— 不能用来验证凭据**

| 场景 | HTTP | 业务 code | 判定 |
|---|---|---|---|
| 有效 `Authorization` | 200 | 200（含 `seatList`） | 查询被受理 —— **但不代表登录有效** |
| **完全不带** `Authorization` | 200 | 200（含 `seatList`，与上一行**同样多**） | 无法判断（匿名同样放行） |
| 已失效、但格式合法的 `Authorization` | 200 | **1111** | 与匿名请求**逐字相同** ⇒ 无法判断 |
| 伪造签名（JWT 形状合法、签名不对） | 200 | **401** | 服务器**解析不了这个头**，不等于"登录过期" |
| 当天窗口（闭馆后） | 200 | 1111 | `预约开始时间必须大于结束时间` —— 纯业务时间规则 |
| 明天及以后 | 200 | 1111 | `只能预约1天之内的时间(含当天)` —— 纯业务时间规则 |
| 服务端异常 | 200 | 500 | 服务端异常，**不是**认证问题 |

**硬结论**：携带已失效凭据与完全不携带凭据时，这个接口的响应**逐字相同**。
因此 `code=1111 ≠ 认证失败`、`code≠401 ⇒ 认证有效` **两条都不成立**，
它的响应**任何情况下都不能作为"登录有效"的证据**。

**② `GET /stage-api/getInfo`（业务身份接口）—— 唯一可用的凭据判据**

| 场景 | HTTP | 业务 code | 判定 |
|---|---|---|---|
| 凭据被接受 | 200 | 200（含 `user` / `roles`） | **登录有效** |
| 无 `Authorization` | 200 | **401** | 认证失效 |
| 已失效（但格式合法）的 `Authorization` | 200 | **401** | 认证失效（与匿名逐字相同） |

依据不是猜测：**站点自己的路由守卫在登录成功后调用的就是它**（`url:"/getInfo"`，
请求头 `Authorization: "Bearer " + Admin-Token`），并读取响应里的 `user` 与 `roles`。
实测它**明确区分**「被接受」与「未被接受」，这是本项目选择它作为判据的全部理由。

失效时的实际响应体（已实测）：

```json
{"code": 401, "msg": "请求访问：/spacelink/getInfo，认证失败，无法访问系统资源"}
```

**③ 状态码语义取自站点自己的前端错误表（原样引用，不是本项目的推断）**：
`401:"认证失败，无法访问系统资源"`、`403:"当前操作没有权限"`。
因此 **403 不等于「令牌过期」** —— 本项目据此保守停止流程，但如实保留
HTTP 状态与业务 code，**绝不断言令牌过期**。

三条关键结论：

1. **认证失效时 HTTP 状态码仍然是 200**，只在业务 `code` 上体现为 `401`。
   所以「HTTP 200 = 登录成功」在这个系统里是**错误**的判断方式。
2. 服务端**只校验 `Authorization` 请求头**：`Cookie` 单独配错（不发 Authorization）时，
   请求会按匿名放行并正常返回座位；反之 `Authorization` 一错，无论 Cookie 如何都返回 401。
   因此**只配 `HAUT_COOKIE` 时无法验证登录状态**，两个变量都要配。
3. `code=1111`/`404`/`500` 与认证无关，**绝不能**据此判断「掉登录」，
   否则会把「时间不合法」「服务器抖动」误报成会话失效。

### 认证预检

正式预约流程开始前（以及每次刷新座位前），程序做一次**只读**预检，返回三态结论：

1. **先问业务身份接口** `GET /stage-api/getInfo`：`code=200` 且响应里**确实带着
   `user` / `roles`** ⇒ `valid`（页面/命令行会写明「凭据已被业务接口接受」，
   只报字段名与条数，**绝不显示任何字段值**）；业务 `code=401`（或 HTTP 401/403）
   ⇒ `invalid`；其余（网络/服务端/结构异常）⇒ 继续第 2 步。
2. **身份接口没给出确定结论时**，再补一次只读座位查询作为第二意见。它自己**不能**
   验证凭据（见上表 ①），只在「服务器拒绝了 Authorization 头」时把结论收紧为
   `invalid`。身份接口一旦判出 `valid`/`invalid` 就**不再发它**：结论不会变，
   白白多打一个请求。
3. 三态含义：
   - `valid` —— 已确认凭据可用（业务接口返回了正常身份数据）；
   - `invalid` —— **已确认凭据未被接受**（HTTP 200 + 业务 `code=401`，或 HTTP 401/403、重定向）
     → **立即停止本次流程**：不轮询座位、不提交预约，并输出中文更新指引（退出码 3）；
     注意 403 的措辞会**明说不断言令牌过期**（见上表 ③）；
   - `indeterminate` —— **无法确认**（网络故障、超时、服务端 5xx、响应结构异常、身份接口
     返回 200 但没有身份字段）→ 只告警、**不当作失效**，避免把网络抖动误判为掉登录。

提交预约时若返回 `code=401`，同样判为 `auth_failed` 并立即停止，
**绝不会**把认证失效当成「可重试的失败」而反复提交，也**绝不会**误报预约成功。

**面板里的远程浏览器采集也走同一条判据**：从远端页面取到 `Admin-Token` **不等于**
登录成功，程序会进入 `verifying` 状态、用 `/getInfo` 验证，**只有验证通过才写快照**；
没通过就如实报「凭据未被业务接口接受」且**不写任何快照**（原有凭据保持不变）。

**预检结果的复用窗口**（`HAUT_AUTH_CHECK_TTL_S`，代码默认 `0` = 关闭）：无人值守的
调度器/运行器在同一个凭据 + 同一个时段/区域的重复预检，可在窗口内复用上一次的结论，
避免一次触发链路里同一次登录被反复探测。三条边界写死在实现里：

- **只复用 `valid`** —— `invalid` / `indeterminate` 一律重新真实探测（安全闸门不得因缓存变松）；
- **键里含凭据指纹** —— 换快照、换 `.env` 即刻失效，不需要额外的清缓存钩子；
- **人点出来的检查永远是真探测** —— 面板的「重新检测登录状态」与
  `python -m haut_seat check-auth` 都先清缓存，不会拿旧结论搪塞人。

缓存只在**进程内存**里，重启即空，**从不落库**（所以重启后绝不会继承「上次有效」）。

### 凭据来源与优先级

凭据有**两个来源**，`HAUT_AUTH_SOURCE` 有**三个取值**（默认 `auto`）：

| 取值 | 行为 | 适用 |
|---|---|---|
| `env` | **只用** `.env` 的两行；连快照文件都不读 | "我要完全手动控制"，与引入本功能之前**逐字节一致** |
| `browser` | **只用**快照；快照缺失/损坏时**明确报错并阻断提交**，**绝不回退 `.env`** | "我不想让过期的手抄凭据被悄悄用上" |
| `auto`（默认） | 两边**较新的一方**胜出 | 一般情况 |

`auto` 的"较新"用真实信号判定：比较快照的 `captured_at` 与 `.env` 文件的 mtime。
**故意不发明"凭据寿命上限"** —— `Admin-Token` 解码后只有 `login_user_key`，
没有 `exp`/`iat`，服务端会话时长也未知，客户端任何"多久算过期"都是猜测。
凭据到底还有没有效，由只读预检**真实探测**（业务身份接口 `/getInfo` 未被接受时返回业务 `code=401`）来回答。

**在哪个页面/命令里看当前来源**：`python -m haut_seat status`、`auth-status`、
面板的 `/admin/auth`（「凭据来源」卡片）与 `/admin/system`（紧凑卡片）。

#### 快照是什么，为什么必须显式存一份

网页登录后令牌写在 `Admin-Token` 这个 **session cookie** 里（没有 `expires`/`max-age`）
—— 也就是说它**不会**被浏览器的持久化 profile 保存下来。所以持久化用户目录只能
**减少重复登录的次数**（少输几次验证码），**不能充当凭据来源**；令牌必须由程序
在登录后**显式取出来**，存成一份权限受限的快照：

```jsonc
// data/auth/credentials.json（已被 .gitignore 排除；字段刻意最小）
{ "version": 1, "source": "browser-login", "base_url": "…",
  "captured_at": "2026-10-18 17:50:12",
  "cookie": "Admin-Token=<jwt>", "authorization": "Bearer <jwt>" }
```

不存账号、口令、验证码答案、`exp`（本来就没有）。页面**只读这张表里的元数据**
（来源 / 采集时间 / 指纹），物理上不可能打开这个文件 —— 这是"不把 Cookie/Token
渲染到前端"的结构性保证。指纹是令牌 sha256 的前 12 位，用于指认"用的是哪一份"，
高熵随机串的前缀**不可反推**。

**关于文件权限（如实说明）**：`os.chmod(..., 0o600)` 在 Linux/macOS 上确实产生
"仅属主可读写"。**在 Windows 上 POSIX 权限位不生效**，`chmod` 只映射到只读位，
真正的访问控制继承父目录 ACL —— 所以不宣称"Windows 上已限制为仅本人可读"。
Windows 上的实际防护是三条：文件在用户目录内、`data/` 被 `.gitignore` 排除、
以及程序从不打印任何值。需要更强隔离时可自行执行：

```bat
icacls data\auth\credentials.json /inheritance:r /grant:r "%USERNAME%:F"
```

（`F` 而不是 `R`：每次重新采集都要用 `os.replace` 换掉这个文件，只读会直接失败。
该命令也会一并去掉 `Administrators`/`SYSTEM` 的继承权限，**是否可接受由你自己判断** ——
这也是本项目**不自动执行**它的原因：`icacls` 受系统语言影响、失败面大。）

### 更新凭据的方式一：浏览器辅助的人工登录（推荐）

它把"开 F12 → 翻 Network → 手抄两个值 → 改 `.env` → 重启"变成
**"点一下 + 在窗口里输一次验证码"**。

```bash
pip install -e ".[auth]"     # 装 Playwright 的 Python 包；**不下载任何浏览器**
python -m haut_seat auth-login
```

之后：

1. 程序弹出系统已装的 **Edge** 窗口并打开 <https://wslib.haut.edu.cn/>；
2. **你本人**在窗口里正常登录（出现图形验证码时由你本人识别）；
3. 登录成功、令牌出现后，程序自动把它取回来、存成受限快照，**窗口随即关闭**；
4. 终端只打印**采集时间与指纹**，绝不打印令牌本身。

```bash
python -m haut_seat auth-status   # 确认"本次实际使用：浏览器会话快照"
```

面板上也可以点：`/admin/auth` → 「一键人工登录」→「打开登录浏览器」。
点击后服务端只**登记状态并起一个脱离进程**（浏览器绝不在 HTTP 请求线程里跑），
页面每 5 秒自动刷新一次等待态。**服务器没有桌面时改用同页的
[「远程浏览器登录」](#远程浏览器登录服务器没有桌面时用)**，它不要求桌面。

**这是人工登录，不是自动登录。** 本项目：

- 不代填账号口令、不识别也不绕过图形验证码、不绕过任何访问控制；
- 登录过程中**不调用任何预约提交接口**（`addbooking` 之类一次都不会出现）；
- 不把 Cookie / Authorization / Token 写进普通日志、页面或异常消息；
- 采集到的凭据只落在上面那份受限快照里，不进版本库。

**已知局限（如实说明，不假装成功）**：

- 若 Web 服务跑在**没有桌面**的会话里（例如 systemd 服务、Windows 服务 / 会话 0），
  子进程弹不出窗口 —— 此时页面会**明确显示失败原因**并给出两条替代路径：
  命令行 `python -m haut_seat auth-login`（需要图形桌面），或下面的**远程浏览器登录**；
- 浏览器自动化依赖只是**可选依赖**：没装 playwright 时 `.env` 与 `auto` 模式
  完全不受影响，`browser` 模式下只要快照还在也照常工作，只有"重新登录"这一步
  需要它；
- 令牌没有 `exp`、没有 refresh token，**周期性重新登录不可避免**（见下文）。

### 远程浏览器登录（服务器没有桌面时用）

如果你的面板跑在没有图形桌面的服务器上，上面那条路必然失败（`headless=False` 弹不出窗口）。
这时用面板里的 `/admin/auth` → 「远程浏览器登录」：

- 服务器端跑**无头 Chromium**，登录页的画面按固定间隔截图送进面板页面；
- 你的鼠标点击、滚轮、键盘输入被转发到远端页面，所以**怎么操作还是你说了算**；
- **图形验证码仍由你本人识别**：本项目不代填账号口令、不识别也不绕过验证码，
  登录过程中**不调用任何预约提交接口**；
- 登录成功后浏览器自动关闭，令牌走**与命令行完全相同的那条凭据链**
  存成受限快照，并做一次**只读**认证预检把结论显示在页面上；
- 页面里**没有任何输入框**：学校的账号口令只敲进远端页面，不进我们的表单、
  浏览器自动填充与历史记录。

**如实说明的限制**：全局只允许**一个**会话（谁先开始谁持有，别人看不到画面也发不了输入）；
不支持按键长按重复、不支持鼠标拖拽选中文字、双击会被远端当成两次单击；画面有刷新间隔，
操作有延迟。**明文 HTTP 下风险被抬高**：链路上除了面板会话 Cookie 和登录页画面，
还多了学校口令的按键 —— 页面顶部会红字告警并给出两条零成本缓解（`ssh -L` 隧道，
或反代 + TLS）；也可以用 `HAUT_AUTH_REMOTE_ALLOW_INSECURE=false` 直接禁止明文下启动。

部署（装 Chromium、单元里两个环境变量、沙箱排查阶梯）见
[`docs/web-deploy.md`](docs/web-deploy.md) 第 6 节；设计与边界见
[`docs/auth-recon.md`](docs/auth-recon.md) 第 6 节。

### 更新凭据的方式二：手动填写 `.env`（回退方案）

不装任何额外依赖的纯手动路径，**始终可用**：

1. 浏览器打开 <https://wslib.haut.edu.cn/>，用统一身份认证账号正常登录。
2. `F12` → `Network` → 刷新页面或点一次「座位预约」→ 任选一个 `/stage-api/` 请求。
3. 复制该请求的 `Authorization` 请求头完整值（形如 `Bearer xxx.yyy.zzz`），
   以及 `Cookie` 请求头里 `Admin-Token=` 那一段。
4. 编辑项目根目录的 `.env`，覆盖这两行（不加引号；`.env` 已被 git 忽略）：

   ```bash
   HAUT_AUTHORIZATION=Bearer <新值>
   HAUT_COOKIE=Admin-Token=<新值>
   ```

5. **验证是否更新成功**：

   ```bash
   python -m haut_seat check-auth
   ```

   - `登录预检: valid — 登录有效（只读接口返回 N 个座位）` → 已恢复，可以重新运行 `book`；
   - `登录预检: invalid …` → 复制有误或令牌已失效，重做第 1–4 步；
   - `登录预检: indeterminate …` → 不是失效判定（网络/服务端问题），稍后重试。
6. 验证通过后再运行 `python -m haut_seat book`。

> `check-auth` 只发一次只读查询，**不会提交任何预约**；输出只显示「已配置/未配置」，不显示凭据值。
>
> 若 `HAUT_AUTH_SOURCE=browser`，手工改 `.env` 是**不会**被采用的（那就是这个取值的含义）。
> 想让两边"谁新用谁"，用 `auto`。

### 为什么不做自动续期 / 为什么预约路径绝不自动拉起浏览器

- 令牌内**没有 `exp`**，客户端无法预知过期时刻；会话存活由服务端决定（实测不可见）。
- 响应**没有** `Set-Cookie`、**没有** refresh token，前端定义的接口列表里
  **也没有任何刷新端点**（已核对，见 [`docs/auth-recon.md`](docs/auth-recon.md)）。
  在拿到真实证据之前，本项目**不猜测**续期接口、参数或返回字段。
- 会话在线时长尚未测出可靠数值（无凭据、不可重复的观测不足以定论），
  因此不实现「定时自动刷新」这类会引入不稳定性的机制。

**预约路径（`book` / 调度器 / 运行器）从头到尾只读快照，绝不拉起浏览器。** 四条理由：

1. 预约路径**无人值守**，而登录必须有人的眼睛看验证码 —— 在无人值守的路径里
   起一个需要人操作的窗口，只会留下一个卡住的进程；
2. 服务 / 无桌面环境里根本拉不起来，会把本可清晰判定的「认证失效 → 等待认证」
   变成运行期异常；
3. 一旦允许，下一个自然诱惑就是自动填表、自动识别验证码 —— 那正是本项目的红线；
4. 认证失效的正确动作是**立即停止提交并转人工**，而不是在提交路径里起一个交互式副作用。

> 若后续确认存在官方刷新机制，可在 `haut_seat/core/auth.py` 的判定基础上扩展；
> 当前阶段以「预检 + 失效即停 + 人工登录/手动更新」为最可靠方案。

### 关于账号密码自动登录

**依旧不支持，且不建议启用。** 理由：

- 登录确实**存在图片验证码**：登录接口要求 `code` + `uuid` 两个参数，
  验证码图片来自 `GET /stage-api/captchaImage`（详见
  [`docs/auth-recon.md`](docs/auth-recon.md)）。识别验证码属于「绕过验证码」，
  明确不在本项目范围内；而人工输入意味着自动登录**无法无人值守**。
- 验证码的**出现条件尚未实测**（是否始终必需、失败几次后才出现、是否与设备/IP 相关），
  在拿到证据之前不据此设计任何流程。
- 需要把学号密码落到本机，一旦落盘即为长期风险；本项目不把账号密码写入源码、
  配置示例、日志或测试文件，也不发送到任何第三方服务。
- 会话刷新机制未确认（见上），自动登录仍无法解决「会话中途失效」。

**"浏览器辅助的人工登录"与"账号密码自动登录"是两件事**：前者由**你本人**在窗口里
完成登录（含验证码），程序只负责把结果取回来存好；后者需要程序自己去提交口令并
处理验证码 —— 后者明确不做。

侦查的完整事实与未知项见 [`docs/auth-recon.md`](docs/auth-recon.md)，
其中也列出了**如果以后要推进**的建议顺序——第一步应该是「人看一次真实登录请求」，
而不是写代码。

如确有需要，正确的做法是本地交互式输入 + 权限受限的本地凭证存储（如系统密钥环），
且必须在不绕过验证码的前提下另行评估。

## 多用户：每人用自己的图书馆账号（用户端 `/booking`）

> 这一节讲的是**同一个部署、多个不同的人**各自登录**自己**的图书馆账号。
> 它由用户端 `/booking`（自助注册 + 绑定 + 自己的预约）与管理端 `/admin/users`
> （邀请码、停用、删除、重置口令）组成。

### 两套账号，绝不混用

| | 平台账号（本项目的账号） | 学校账号（图书馆账号） |
|---|---|---|
| 用途 | 登录 `/booking`，决定"哪些计划是我的" | 决定"预约提交在谁名下" |
| 怎么来 | 自助注册（**需要邀请码**） | 用户在绑定页输入学校学号/工号与口令 |
| 口令存哪 | **只存 scrypt 哈希** | **一个字节都不落盘**（见下） |
| 忘了怎么办 | 管理员在 `/admin/users` 重置 | 用户自己重新绑定一次 |

**平台口令 ≠ 学校口令。** 两者在任何代码路径上都不相交：前者进 `app_user.password_hash`，
后者只在那一次绑定请求的内存里存在。管理员**看不到、也不需要看到**任何人的学校口令。

### 用户怎么一步步用起来（手机浏览器即可完成）

1. **管理员开通入口**：打开 `/admin/users` → 「生成邀请码」→ 把邀请码发给要注册的人。
   （自助注册默认**关闭**，必须由管理员在页面上打开。）
2. **注册**：手机打开 `https://<你的域名>/booking/register`，填用户名、口令、邀请码。
   注册**不会自动登录**（否则"口令输错了"看起来会像"注册失败"）。
3. **登录**：`/booking/login`，用**平台账号**登录（不是学校账号）。
4. **绑定图书馆账号**：在 `/booking/bind` 里填写
   **学校账号（学号/工号）+ 学校口令 + 图形验证码**。
   - 验证码图片由服务器从学校官方接口 `GET /stage-api/captchaImage` 取回**原样转发**
     给页面，所以你**在手机上照样看得到、能输入** —— 不需要把手机浏览器的 Cookie
     取出来交给服务器，也不需要装任何东西。
   - 提交后服务器用它**一次性**调用学校官方登录接口
     `POST /stage-api/login4web2HGD`（`{username, password, code, uuid}`），
     成功（`code == 200`）才把你自己的 `Cookie` / `Authorization` 取回来加密保存。
   - **不识别验证码、失败不重试**（重试本质就是对验证码的暴力尝试）：
     图形看不清就刷新页面换一张，重新输入。绑定尝试本身有次数限制。
5. **建计划**：`/booking/new` 建自己的预约计划；只能看到、只能改自己的计划。
   别人的计划 id 直接访问得到的是 **404**（不是 403 —— 403 会泄露"这个 id 存在"）。
   - **座位不用手抄**：点表单里的「从座位目录挑选」进入 `/booking/catalog`，
     按区域 / 楼层 / 座位名勾选，座位名与**它所属的区域 ID** 会自动填进计划表单；
     上移/下移决定的顺序就是它们写进「候选座位」的顺序（表单里越靠前越先尝试）。
   - **你挑的座位只属于你**：草稿记在 `user_seat_pick` 里并按 `user_id` 隔离 ——
     你看不到、也改不动别人的草稿（包括管理端自己那份）；保存计划时会清空你自己的草稿
     （座位已经写进计划里了），他人的一律不受影响。
   - **目录是填表助手，不是第二个真相来源**：提交时仍然只认计划表单里的内容。
     目录里有没有这个座位，都改不动"它到底可不可预约"（见「座位状态语义」）。
     目录为空时不挡路：仍可手工填区域 ID 与座位名（区域 ID 也可在高级设置里直接输入）。
     目录由管理员在 `/admin/catalog` 拉取；用户端**没有**更新/导入/收藏等管理能力。
6. **看状态**：`/booking` 上能看到"等待认证"这类状态。
   **你自己的凭据失效只会停掉你自己的计划**，别人的照跑，绝不会改用别人的账号。

### 凭据怎么存、怎么隔离

- 每个用户一行 `user_credential`：`cookie_enc` / `authorization_enc` 是**经认证加密**后的
  密文（`services/credential_crypto.py`：scrypt 派生密钥 + SHAKE256 密钥流 + HMAC-SHA256，
  **先验标签再解密**），AAD 里绑定了 `user_id` 与字段名 ——
  因此**把一个用户的密文搬到另一个用户名下必然解不开**。
- 明文只在内存里：解出来就交给 HTTP 客户端，不进日志、不进异常消息、不进模板上下文。
- **页面拿不到密文**：管理端读的是 `repo.get_user_credential_view`，那份查询里根本没有
  密文列；页面只显示学校账号标识、有效性和**指纹前缀**（sha256 前 12 位，单向不可逆）。
- **执行时严格各用各的**：调度器为每个计划解密**它属主自己**的那一份凭据，
  取不到 / 解不开就**停下并提示重新登录**，绝不回退到 `.env`、快照或别人的账号。
  出站 HTTP 客户端本来就按凭据指纹分桶，因此不同账号天然不共用连接与会话。
- 无主的计划（引入用户端之前的历史计划、管理端自己建的计划）仍沿用 `.env` / 快照
  那一份全局凭据 —— 与从前逐字节一致。

### ⚠️ 主密钥必须备份

每用户凭据的加密主密钥在 `data/auth/master.key`（或由 `HAUT_AUTH_CRED_KEY` 提供，
简写 `HAUT_CRED_KEY` 也认）。

> **删掉或换掉它，所有人已保存的凭据都将无法解密**，每个人都必须重新绑定一次。
> 这是刻意的：解密失败时系统**不会**悄悄换用别人的账号或旧的全局凭据，而是
> 把该用户的计划转入「等待认证」并提示重新绑定。
> 请把 `master.key` 纳入你的备份（与 `data/web.db` 一起），并**不要**提交进版本库。

### 管理端能看到什么

`/admin/users` 显示每个用户的用户名、状态、计划数、**绑定的图书馆账号（学号/工号）**、
凭据有效性、指纹前缀与绑定时间；`/admin`、`/admin/plans`、`/admin/runs` 及两个详情页
都有「所属用户」列，运行记录因此能一路追到"这次提交用的是谁的账号"。

管理员可以**停用**（立即作废其全部会话，计划不会被执行）、**删除**（**保留**其计划与
运行记录 —— 它们是"今天是否已提交过"的证据，只解除归属）、**重置口令**（其会话全部作废）。
管理端**不显示**任何人的凭据明文，也没有这个能力。

### 尚未解决的限制（如实说明）

- **学校站点没有 OAuth / CAS / 授权回调**（已核实，见
  [`docs/auth-recon.md`](docs/auth-recon.md)），所以"用户本人完成一次官方登录"是唯一
  可行路径；因此**无法做到"用户无需露面就自动拿到凭据"**。
- **会话时长未知、没有 refresh 接口**，所以凭据到期后必须由本人重新绑定一次；
  不做"自动续期"，也不在预约路径里偷偷拉起浏览器（理由见上一节）。
- 绑定页需要用户输入**学校口令**——它只在内存里过一遍，但"用户是否愿意在本服务里
  输入学校口令"是一个信任问题，不是技术问题。不愿输入的人只能继续用 `.env` 模式
  （单人）或自行在服务器上跑 `auth-login`。
- 依 `.env` 的 `HAUT_AUTH_DIR` 位置，`data/auth/` 目录在 **Windows 上没有 POSIX
  权限位**（`chmod 0600` 只影响只读位），真实防护来自"在用户 profile 内的项目目录里、
  被 `.gitignore` 排除、从不打印值"。Linux 上确为 `0600`。

## 座位状态语义（重要）

`seatStatus`、`isCan`、`open` 的**具体含义尚未验证**，程序不会据此自动判定某座位可预约。

- 只有把验证过的「(seatStatus, isCan, open)」三字段组合填入
  `config/seats.json` 的 `confirmed_bookable_states` 后，对应座位才会被标记为
  `confirmed_bookable`。
- 默认该数组为空 → 所有座位均为 `unknown`，**不会被自动认定为可预约**。
- 取值需与接口 JSON 的原始类型一致（数字就填数字、字符串就填字符串）。

## 已观察到的服务器行为（预约时间窗口）

以下来自真实只读查询记录，仅记录事实，**不构成已确认的规则**。

### 真实观察

- 查询返回 HTTP 200，但业务 `code=1111`，`msg="只能预约1天之内的时间(含当天)"`。
- 该次查询时段 `2026-10-16 10:00:00` → `2026-10-16 10:30:00`，请求时间约 `2026-10-15 22:48`。
- 同一 `code=1111` 此前还观察到另一条 `msg="预约开始时间必须大于结束时间"`（查询时段为前一天）。

### 合理推测（未证实）

- 服务器对预约时间存在“约 1 天之内（含当天）”的窗口限制。
- 上例目标时段距请求时刻超过 24 小时，可能是被拒的原因。

### 与官方规则的对照

- “查询次日时段（`2026-10-16`）被 `code=1111` 拒绝”与官方「读者只可预约当天座位」**一致**。
- 但注意措辞差异：官方说法是“当天”，接口错误文案是“1 天之内(含当天)”；接口校验的确切机制（自然日边界、跨零点、是否按 24 小时滚动）**仍未确认**，暂以官方说明为准、接口机制待实测确认。

### 未验证事项

- 窗口的具体边界：是否严格 ≤24 小时、是否按自然日计算、跨零点如何界定。
- `code=1111` 是否复用同一错误码承载多种语义（超出窗口 / 起止顺序）。
- 服务端错误文案是否与真实规则一致。

> 处理原则：**不据此自动改写查询时间，不增加自动时间枚举。** 时间规则以学校官方说明或受控只读验证为准。

## 真实预约前需确认（差距清单）

实现并启用 `addbooking` 之前的唯一依据。区分「已确认（有证据）」与「待确认（必须核实）」。

### 已确认（有证据）

- 查询接口：`GET /stage-api/api/seatbook/layout/query`；query 参数 `pageNum`、`pageSize`、`regionid`、`starttime`、`endtime`（`YYYY-MM-DD HH:MM:SS`）；**无 `channel`**。
- 请求头：`Accept`、`Accept-Language`、`Referer`、`User-Agent`（非敏感），以及 `Cookie` / `Authorization`（凭据）。
- `regionid=16` 正常返回座位（座位名「五层东书库南区」，共 70 个）。

## 预约任务（book）

`book` 命令执行一次完整的预约流程：**认证预检 → 等待触发时刻 → 查询选座 → 提交（含失败重试/换座）**。
只有在 `HAUT_ENABLE_REAL_BOOKING=true` 且无暂停旗标时才会走到提交分支。

```bash
cp config/booking.json.example config/booking.json   # 编辑 regionid / 时间 / 目标座位
python -m haut_seat check-auth                       # 先确认凭据有效
python -m haut_seat book
```

- 时间不合法会立即停止并给出原因（返回码 2）。
- **认证预检**在可能的长时间等待之前执行：失效立即停止（返回码 3），
  不会白等到窗口开放才发现凭据过期；进入提交窗口前的每次刷新查询也会重新把关。
- 同一时刻重复触发会被文件锁拦下（防并发/重复预约）。
- 选出的座位若未人工核实，一律标 `unknown`，不会被当作可预约。
- 认证失效时立即停止：不轮询座位、不提交预约、**不重试提交**，也不会误报预约成功。

### 开放时刻之前（07:00 之前）会怎样

官方规则是 07:00 开放、21:30 截止。程序据此在两处把关，**提前启动不会把提交提前**：

- **07:00 之前只做只读查询，绝不提交。** 提前启动（`HAUT_SCHEDULER_TRIGGER_LEAD_S`）
  或窗口内补跑时，运行器会一直等到开放时刻才提交；等待期间按 30 秒重新查询，
  开放那一刻立刻用**最新**的查询结果提交（开放前的候选会被作废，不拿去提交）。
- **开放前查询失败不会结束这次运行。** 查询失败只记录、隔 30 秒重查，直到窗口关闭
  （计划的 `book_end`）；只有认证失效（HTTP 401/403 或业务 `code=401/403`）例外，
  它立即停止并提示更新凭据。
- **服务器明确回复「尚未开放」时**，那一次提交**不计入重试次数、也不结束运行**：
  程序退回只读查询、按 30 秒重试，直到窗口关闭。识别词由 `HAUT_NOT_OPEN_KEYWORDS`
  配置（逗号分隔，**默认空 = 不启用**）—— 服务器「未开放」的真实文案我们从未观察到，
  凭空猜词会把一次**永久性失败**误判成「稍后再试」。首次遇到时，真实文案会原样出现在
  运行事件里（形如「重试次数耗尽(3次)：<服务器 msg>」），把其中稳定出现的片段填进该键。
- **结果未知绝不自动重放**：提交超时、异常或响应无法判定结果时，运行立即停止并记成
  「提交结果未知」，需要人工核实后显式确认才会继续 —— 与从前一致，未被本次改动放松。

> 如实说明的限制：`HAUT_NOT_OPEN_KEYWORDS` 留空时，若服务器在 07:00 之后仍以「未开放」
> 为由拒绝提交，那会被当作普通失败处理（按计划的「单个座位最大尝试次数」重试后停止，
> 且当天不再自动发起第二次提交）。开放时刻本身取自官方规则（窗口当天 07:00）；
> 若学校实际开放时刻与官方规则不符，这一处需要按实测调整。

## Linux 部署

有两种部署形态，**可以共存**（两者共用同一把跨进程锁 `data/book.lock`，
不会同时提交同一时段的预约）：

| 形态 | 适合 | 入口 |
|---|---|---|
| **A. cron + 单次命令** | 只在固定时刻跑一次预约，不需要常驻进程 | `python -m haut_seat book` |
| **B. systemd + Web 面板** | 想在手机上看计划/运行记录，想在页面上改计划 | `python -m haut_seat web` |

### A. cron 触发单次命令

目标是最简单的「系统定时任务触发单次命令」，不需要常驻进程：

1. 部署代码与依赖（见「安装」），把 `.env` 与 `config/booking.json` 放在项目目录（两者均被 git 忽略，凭据只留在本地）。
2. 用 `crontab -e` 在预约开放后（≥07:00）触发一次 `book`，例如每天 07:00:05：

   ```cron
   # 每天 07:00:05 运行一次预约任务；输出追加到 cron.log
   5 7 * * * cd /path/to/haut-seat-helper && .venv/bin/python -m haut_seat book >> logs/cron.log 2>&1
   ```

3. 查看结果：

   ```bash
   tail -f logs/haut_seat.log   # 运行日志（已脱敏，不含 Cookie/Token）
   tail -f logs/cron.log        # cron 触发日志
   ```

4. **长期部署的关键一步：定期检查会话是否还有效**。令牌没有 `exp`，会话失效时刻不可预知；
   定时任务若在失效后运行，只会以退出码 `3` 停止并打印更新指引（不会空转、不会误报成功）。
   建议在预约前先跑一次预检，例如每天 06:50：

   ```cron
   50 6 * * * cd /path/to/haut-seat-helper && .venv/bin/python -m haut_seat check-auth >> logs/cron.log 2>&1
   ```

   看到 `登录预检: invalid` 就当天手动更新凭据（步骤见上文「手动更新凭据」）。

5. 暂停：在项目目录创建 `data/pause.flag`（存在即暂停一切真实预约），删除即恢复。

### B. systemd 常驻 Web 面板

```bash
sudo cp deploy/haut-seat-web.service /etc/systemd/system/
# 按实际情况修改 User / Group / WorkingDirectory
sudo systemctl daemon-reload
sudo systemctl enable --now haut-seat-web
```

面板**只监听 127.0.0.1**，对外访问请配 nginx + HTTPS：
`deploy/nginx-haut-seat.conf.example`。启用代理后至少要改一项并重启服务：
`HAUT_WEB_SESSION_SECURE=true`（**必须**，否则 Cookie 没有 `Secure`）。
`HAUT_WEB_TRUST_PROXY` 保持 `false` 也能拿到真实来源 IP，只有在你确认服务无法被
绕过代理直连时才需要考虑置 `true`。日志轮转见 `deploy/logrotate-haut-seat.example`。

备份、恢复、手动配置检查清单、需要人工介入的场合：见
[`docs/web-deploy.md`](docs/web-deploy.md)。

> 注意：`book` 现在会不会真的提交预约，取决于 `HAUT_ENABLE_REAL_BOOKING` 与暂停旗标；
> 无论走 CLI 还是面板，认证失效时一律立即停止，且**不会**把「提交结果未知」当成失败自动重试。
